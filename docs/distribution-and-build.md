# 배포 & 빌드 모델 — 팀원 직접 빌드 (Drive 동기 + 원클릭 인코딩 임포터)

> **결정(사용자)**: 팀원이 인코딩만 하고 끝내는 게 아니라, **팀원이 직접 유니티로 빌드하며 QC**한다.
> 직접 빌드·시연하는 과정 자체가 품질검수(QC)의 일부이기 때문. 따라서 "중앙에서 대신 빌드"가
> 아니라 **팀원이 쉽게 직접 빌드할 수 있는 배포**가 목표다. git/zip은 팀원에게 부적절 → 대안 정의.

---

## 0. 두 개의 표면 (역할이 아니라 도구가 나뉜다)

| 표면 | 하는 일 | 필요 환경 |
|---|---|---|
| **PIMM UnityGameCreator (HTML)** | 게임 설계 · 배치 · 소리/메모 · **인코딩(내보내기)** | 브라우저만. 설치 0 |
| **PIMMplayer (Unity 프로젝트)** | 인코딩을 받아 **직접 빌드·Play로 QC**, 최종 빌드 | Unity + 핌플레이어 프로젝트 |

팀원은 **둘 다** 만진다(설계는 HTML, 빌드/QC는 Unity). 문제는 "Unity 프로젝트를 어떻게 쉽게
팀원에게 최신 상태로 주느냐"인데, **git도 매번-zip도 아니다.**

---

## 1. 배포 방식 — Google Drive 동기 프로젝트 (git·zip 불필요)

우리는 전원 **구글드라이브 데스크톱 앱**을 쓴다(로컬 경로로 접근 가능). 이걸 그대로 배포 채널로.

```
[공유 드라이브] PIMMplayer_Project/           ← 개발자가 여기만 최신 유지
   ├─ Assets/                (핌플레이어 씬·프리팹·C#·StreamingAssets)
   ├─ Packages/
   └─ ProjectSettings/
        │  Drive 데스크톱 앱이 자동 동기
        ▼
[팀원 A PC] 로컬 동기폴더의 PIMMplayer_Project/ → Unity Hub로 열기 → Play/Build
[팀원 B PC] 〃
```

- **개발자가 프로젝트를 한 번 업데이트 → Drive가 전원에게 자동 동기.** zip을 매번 만들 필요 없음.
- 팀원은 **git 명령 0개.** Drive 폴더의 프로젝트를 Unity Hub로 "Open"만.
- **동기 대상 최소화**: `Assets/` + `Packages/` + `ProjectSettings/`만 공유한다.
  `Library/`·`Temp/`·`Logs/`·`obj/`·`.git/`은 **동기 제외**(용량 크고 로컬 재생성됨). Drive 앱의
  "폴더 제외" 또는 프로젝트에 `.driveignore` 관례 문서화. Unity가 처음 열 때 `Library`를 로컬 재생성.
- 충돌 방지: 팀원은 프로젝트를 **읽기 전용 원본**으로 두고, 자기 게임 작업물(인코딩에서 들어온
  StreamingAssets/에셋)은 **자기 로컬 사본**에서 빌드. 공유 원본을 직접 편집하지 않게 가이드.

> 대안(팀원이 git에 익숙해지면): GitHub Desktop 1클릭 sync, 또는 사내 배포 도구. 하지만 현 시점
> **Drive 동기가 추가 학습 0**으로 가장 쉽다.

## 2. 빌드를 쉽게 — 원클릭 "인코딩 임포터" (Unity Editor 스크립트)

팀원이 인코딩파일을 유니티에 손으로 배선하면 어렵다. 그래서 **핌플레이어 프로젝트에
Editor 메뉴 하나**를 넣는다(개발자가 1회 구현, 이후 팀원은 클릭만).

```
Unity 상단 메뉴:  PIMM ▸ 게임 인코딩 불러오기…
   → 인코딩파일(.pimmgame.json) 선택
   → 임포터가 자동으로:
       1) 임베드된 에셋이미지/오디오를 프로젝트 폴더로 추출
       2) StreamingAssets에 config(theme_config/config/input_registry/defaults) 기록
       3) 좌표(unity.anchorMin/Max)로 RectTransform 배치 (또는 런타임 로더가 소비)
       4) BGM/SFX 배선, 프리팹 인스턴스 배치
   → [Play]로 즉시 시연·QC → 문제 없으면 [Build]
```

- **리스킨 게임(기존 5메커니즘 재사용)**: 임포터가 config+에셋만 갈아끼우면 끝 → **C# 수정 0**, 팀원이 바로 Play/Build로 QC.
- **신규 메커니즘 게임**: 임포터가 "이 인코딩은 기존에 없는 메커니즘 X를 요구함"이라고 **명확히 플래그** → 이 부분만 Cowork(또는 개발자)가 C#을 추가. 나머지 리스킨 부분은 임포터가 처리하므로 개발 범위 최소.
- 이 임포터가 "코드 변환 임팩트 최소화 + 에셋 위주"라는 품질기준을 강제하는 장치다.

> 임포터 스크립트는 **PIMMplayer repo(별도)**에 들어간다. 이 repo가 세션에 마운트되면 구현한다.
> 현재는 인터페이스(인코딩 스키마 ↔ StreamingAssets 매핑)만 확정해 둔다 → `encoding-and-build.md`.

## 3. "매번 다른 게임이라 리스킨 불가" 문제에 대한 정직한 정리

- **사실**: 순수 리스킨은 "이미 플레이어에 있는 메커니즘"에서만 된다. 게임이 계속 새로우면 새
  C#이 불가피하고, 수백 개를 미리 넣어둘 수는 없다.
- **그래서 리스킨을 "가능한 넓게" 만드는 두 축**:
  1) **인코딩 임포터**가 리스킨 부분(레이아웃·에셋·소리·좌표·프리팹 인스턴스)을 전부 자동 처리 →
     사람이 만질 코드가 **정말 새로운 규칙**으로만 줄어든다.
  2) **엔진 일반화(장기 투자)**: 핌플레이어를 입력→규칙→피드백의 **파라메트릭 프리미티브**로
     일반화하면, "새 게임"의 상당수가 여전히 config로 표현된다(신규 C# 빈도↓). → 별도 과제.
- **결론**: 신규 코드를 0으로 만들 순 없지만, **팀원이 직접 빌드/QC하는 흐름은 유지하면서**
  손대는 코드량을 임포터+엔진일반화로 최소화한다. 새 메커니즘이 필요한 순간만 Cowork가 개입.

---

## 4. 팀원 관점 최종 플로우 (설치 최소)

```
1) HTML 게임크리에이터 열기(설치 0) → 게임 설계 → 인코딩(.pimmgame.json) 저장
2) Unity Hub로 Drive 동기폴더의 PIMMplayer 프로젝트 열기(git 0, zip 0)
3) 메뉴: PIMM ▸ 게임 인코딩 불러오기 → 인코딩파일 선택
4) Play로 시연·QC (여기서 팀원이 직접 품질 확인)
5) 문제 없으면 Build / 있으면 HTML로 돌아가 수정 후 재인코딩
   └ 새 메커니즘이 필요하다고 임포터가 플래그하면 그 부분만 Cowork 요청
```

- **설치할 것**: Google Drive 데스크톱 앱(이미 사용) + Unity Hub/Editor(1회). 그게 전부.
- **안 하는 것**: git 클론, 매번 zip 수령, 서버 셋업(HTML은 서버 없이도 동작).

---

## 5. 로드맵 반영
- 인코딩 포맷(PART 9)을 **StreamingAssets 드롭 + 임포터 소비**에 맞춰 설계 → `encoding-and-build.md`.
- PIMMplayer repo 확보 시: **인코딩 임포터(Editor 스크립트)** + **런타임 레이아웃/에셋 로더**(리스킨을
  리빌드 없이) 구현.
- Drive 프로젝트 배포 가이드(동기 제외 목록·읽기전용 원본 규칙)를 팀원 온보딩 문서로.
