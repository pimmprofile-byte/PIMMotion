## 1. 게임이 뭔가 (한 장)

방탈출 테마 안에서 돌아가는 **서브게임**입니다. 유니티(핌플레이어)로 빌드되고, 물리 장치와 시리얼로 연결됩니다.

```
시리얼 신호로 시퀀스 진입
  → 캐릭터 등장 + 룰렛
  → 20종 중 1종 추첨
  → 화면에 퍼즐 가이드 표시
  → 플레이어가 퍼즐을 푼다              ← 여기가 이번 작업
  → 코드(또는 열쇠)를 얻는다
  → 해당 자물쇠를 연다
  → 함 안의 버튼을 누른다 = 해금
  → 캐릭터/악세서리 착용 → 다음 라운드
20종 전부 해금하면 클리어. 점수가 매겨진다.
```

**20종 = 5카테고리 × 4.** 현장 자물쇠함이 4열×5행 버튼 그리드이고, 가로 행이 카테고리입니다.

```
        col1   col2   col3   col4
row1  [ E01 ][ E02 ][ H01 ][ H02 ]   캐릭터   ← H02가 이번 작업
row2  [ E03 ][ E04 ][ H03 ][ H04 ]   장신구
row3  [ E05 ][ E06 ][ H05 ][ H06 ]   무기
row4  [ E07 ][ E08 ][ H07 ][ H08 ]   상의
row5  [ E09 ][ E10 ][ H09 ][ H10 ]   하의
             저난도(미정)   고난도(확정)
```

## 2. 바꾸면 안 되는 제약

이미 확정됐고 현장 장치가 물리적으로 존재합니다. 퍼즐이 여기 맞춰야지 반대가 아닙니다.

| 항목 | 확정 내용 |
|---|---|
| 진행 구조 | 20문제 **전부** `퍼즐 → 코드 획득 → 자물쇠 → 함 버튼 → 해금` |
| 자물쇠 | **20개** (카드마다 1개). 정답이 고정 상수 — 라운드마다 재설정하지 않음 |
| 버튼 그리드 | 정답 입력기가 **아님**. "수령 확인 + 카드 선택"용 |
| 램프 | 개별 제어 **불가**. 해금 상태는 화면 UI가 표시 |
| 시리얼 | Arduino Mega, `IN_NN` 포맷, 디바운스 50ms, baud 115200 |

### 장치 목록 (전부)
| 장치 | 수량 | 배정 |
|---|---|---|
| 줄당기기 (리미트스위치) | **2** | **H02 ← 이번 작업** |
| 조이스틱 1 + 버튼 5 | 1세트 | H05 |
| 아이템박스 패널 (주황·초록) | 2 | H03 (귀걸이) |
| 로딩바 토막 (노랑·초록·빨강) | 3 (미확정) | H08 |
| 왕버튼 | 3 | 캐릭터 선택 **전용** — 퍼즐 사용 금지 |
| 룰렛 휠 | 1 | 룰렛 **전용** — 퍼즐 사용 금지 |

> 왕버튼·룰렛휠을 퍼즐에 끌어오지 마세요. 이미 시스템 조작 의미가 붙어 있어서, 겸용하면 플레이어가 "이걸 조작하면 룰렛이 도나 퍼즐이 풀리나"를 헷갈립니다. **장치 하나에 의미 하나**가 원칙입니다.

## 3. H02 브리프 — 줄당기기

### 확정 사항
| 필드 | 값 |
|---|---|
| 칸 | R1 · C4 |
| 카테고리 | 캐릭터 |
| 보상 | `CHR_04` (캐릭터 4번 — 이름·외형 미정) |
| 난이도 | 고난도 |
| 풀이 방식 | **조작부** |
| 조작부 | 줄당기기 리미트스위치 **2개** (`DEV_PULL`, IN 2ch) |
| 자물쇠 | **버튼 자물쇠** |
| 가이드 | **G-A** — 단일 이미지 **1520 × 680** 1장 |
| 컨셉 방향 | 당기는 순서로 캐릭터를 **호출**하는 연출 |

### 입력 어휘 — 이게 설계의 실질적 천장
리미트스위치는 **당김/놓음 두 상태만** 감지합니다. 세기도, 거리도, 속도도 없습니다.

```
표현 가능한 것 :  어느 줄(L / R) · 몇 번 · 어떤 순서 · 동시에 당겼는가
표현 불가능한 것 :  얼마나 세게 · 얼마나 오래(정밀) · 얼마나 멀리
```

- 실질 심볼은 **L · R · LR(동시)** 3종 → 길이 n 시퀀스의 공간은 **3ⁿ**
- 디바운스 50ms 표준이라 **빠른 연타는 구분되지 않습니다.** 초당 3회 이하로 가정하세요
- "길게 당기고 있기"는 가능은 하지만 **경계가 모호**해 플레이어가 성공을 확신하기 어렵습니다. 권장하지 않습니다

### 길이 권장
| n | 공간 | 판단 |
|---|---|---|
| 3 | 27 | 너무 쉬움 |
| **4–6** | **81–729** | **적정** |
| 7+ | 2187+ | 기억 부담이 커서 재미가 아니라 스트레스가 됩니다 |

### 조작부 문제의 특권 — 실패를 감지할 수 있습니다
자물쇠로 푸는 문제 6종은 물리 자물쇠라 게임이 실패를 **아예 모릅니다**(타이머 힌트만 가능). 반면 H02는 IN 신호가 오므로 **틀린 입력을 즉시 알 수 있습니다.**

→ 오답 시 부저·화면 점멸·시퀀스 리셋을 설계에 넣으세요. 이게 조작부 문제의 체감을 만드는 부분입니다.

### 산출물 = "코드"입니다
조작부는 **판정기가 아니라 코드를 얻는 수단**입니다. 올바른 조작의 결과로 **버튼 자물쇠 코드가 드러나야** 합니다.

```
줄을 올바른 순서로 당김 → 화면(또는 장치)이 버튼 자물쇠 코드를 드러냄
                        → 그 코드로 자물쇠를 엶 → 함 안 버튼 → 해금
```

### 가이드 이미지 1장의 제약
G-A 단일 이미지 **1520×680** 한 장에 **규칙 설명이 다 들어가야** 합니다. 영상이 아닙니다(영상은 H05만).
텍스트는 유니티 TextMesh로 얹으므로 **이미지에 글자를 그려 넣지 마세요.**

## 4. 산출물 형식

`cards.json`의 `H02` 항목에서 `puzzleContent`를 아래 형태로 채우세요. 나머지 필드(칸·자물쇠·가이드 타입)는 **건드리지 마세요.**

```jsonc
"puzzleContent": {
  "title": "퍼즐 이름",
  "premise": "플레이어가 보는 상황 한 줄",
  "rule": "규칙 — 무엇을 보고 무엇을 당해야 하는지",
  "sequence": ["L","R","LR","L"],      // 정답 조작 순서
  "codeReveal": "올바른 조작 후 코드가 어떻게 드러나는가",
  "lockCode": "버튼 자물쇠에 입력할 값",
  "failFeedback": "오답 시 무엇이 일어나는가",
  "guideImage": {
    "size": [1520, 680],
    "描述": "이미지에 무엇이 그려져야 하는가 (글자 제외)",
    "textOverlay": ["TextMesh로 얹을 문구들"]
  },
  "hints": ["1단계", "2단계", "3단계"]
}
```

## 5. 답을 받아야 하는 것

설계 전에 사용자에게 확인하세요. 이것들이 정해지지 않으면 퍼즐이 성립하지 않습니다.

1. **버튼 자물쇠 사양** — 버튼 몇 개인가, 순서를 기억하는가 아니면 조합만인가, 코드 길이는? → 이게 `lockCode` 형식을 결정합니다
2. **줄이 물리적으로 무엇에 달려 있는가** — 벽? 천장? 당기면 무언가 움직이는가, 아니면 스위치만 눌리는가 → 시각 피드백 설계에 필요
3. **줄 2개가 서로 구분되는가** — 색·길이·위치·라벨. 구분이 안 되면 L/R 시퀀스 자체가 성립하지 않습니다
4. **동시 당김이 물리적으로 가능한가** — 두 줄이 한 사람이 동시에 잡을 수 있는 거리인가. 불가능하면 심볼이 3종에서 **2종으로 줄고** 공간이 3ⁿ → 2ⁿ이 됩니다

> 4번이 특히 중요합니다. 동시 당김이 안 되면 n=6이어도 64가지뿐이라 난이도 설계를 다시 해야 합니다.
